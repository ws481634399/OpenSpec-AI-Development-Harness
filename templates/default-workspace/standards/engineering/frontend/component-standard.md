# 前端组件设计规范

> 版本：v0.1  
> 类型：前端工程规范  
> 作用域：OpenSpec Workspace


# 1. 文档目的


本文档定义前端组件设计、拆分、复用和维护规范。


目标：

- 建立清晰的组件职责边界；
- 提升组件复用能力；
- 降低页面复杂度；
- 保证 AI Coding Agent 能够按照统一规则设计前端组件。


---

# 2. 组件设计原则


## 2.1 单一职责原则


一个组件应该只负责一种明确职责。


组件应该关注：

- UI展示；
- 用户交互；
- 数据接收；
- 状态变化。


不应该：

- 承担大量业务流程；
- 直接管理无关模块状态；
- 包含多个复杂功能。


示例：


推荐：

```
OrderTable

负责：

订单列表展示
```


不推荐：

```
OrderPage

同时负责：

- 查询订单
- 支付
- 导出
- 权限判断
- 数据处理
```


---

## 2.2 高内聚低耦合


组件内部应该保持功能完整。


组件之间应该通过明确接口通信。


推荐：

```
Parent Component

        |

        |

Props / Events

        |

        ↓

Child Component
```


避免：

- 直接修改父组件数据；
- 依赖外部隐藏状态。


---

## 2.3 可复用原则


组件设计应该考虑复用。


但是：

不要为了未来可能复用而过度抽象。


判断是否抽离组件：

满足以下条件之一：

- 多处使用；
- 业务含义明确；
- 结构复杂；
- 独立维护。


---

# 3. 组件分类规范


前端组件分为：


```
基础组件

业务组件

页面组件
```


---

# 3.1 基础组件


位置：

```
components/common/
```


特点：

- 无业务逻辑；
- 高复用；
- 与具体业务无关。


例如：

```
Button

Modal

Table

Form
```


要求：

- 接口稳定；
- 文档明确；
- 不依赖业务数据。


---

# 3.2 业务组件


位置：

```
components/business/
```


特点：

包含业务含义。


例如：

```
OrderStatusTag

ProductSelector

PaymentPanel
```


要求：

- 服务具体业务；
- 明确输入输出；
- 避免跨领域耦合。


---

# 3.3 页面组件


位置：

```
pages/
```


特点：

负责页面组合。


职责：

- 页面布局；
- 数据加载；
- 组件组合；
- 页面级流程。


不应该：

- 沉淀大量通用逻辑。


---

# 4. 组件目录规范


推荐结构：


```
components/

└── OrderTable/

    ├── index.vue

    ├── types.ts

    ├── constants.ts

    └── README.md
```


说明：

|文件|作用|
|-|-|
|index.vue|组件实现|
|types.ts|类型定义|
|constants.ts|组件常量|
|README.md|组件说明|


---

# 5. Props设计规范


## 5.1 Props应该明确


Props应该表达组件需要的数据。


推荐：


```typescript
interface Props {

  orderId: string;

  disabled?: boolean;

}
```


避免：


```typescript
props: {

  data:Object

}
```


---

## 5.2 避免过多Props


当Props数量过多时：

说明组件职责可能过重。


例如：


不推荐：

```typescript
<UserCard

name=""

age=""

address=""

phone=""

email=""

role=""

permission=""
/>
```


应该考虑：

拆分组件。


---

# 6. Events设计规范


## 6.1 事件表达行为


事件名称应该描述动作。


推荐：

```
submit

cancel

select

change
```


避免：

```
event1

click2
```


---

## 6.2 数据流方向


推荐：

```
Parent

↓

Props

↓

Child


Child

↓

Events

↓

Parent
```


避免：

子组件直接修改父组件数据。


---

# 7. 组件状态管理


## 7.1 内部状态


组件内部临时状态：

例如：

- 展开状态；
- 输入状态；
- loading状态。


应该保存在组件内部。


---

## 7.2 业务状态


跨页面或跨组件状态：

应该使用统一状态管理。


例如：

```
UserStore

OrderStore
```


不要：

通过多层Props传递。


---

# 8. 组件通信规范


组件通信方式优先级：


```
Props / Events

↓

状态管理

↓

全局事件
```


避免：

大量使用全局事件。


---

# 9. 大组件拆分规则


出现以下情况应该考虑拆分：


## 9.1 文件过大


例如：

单文件超过：

```
300-500行
```


应该评估拆分。


---

## 9.2 功能过多


例如：

一个页面包含：

```
查询

编辑

导入

导出

权限
```


应该拆分。


---

## 9.3 逻辑复杂


业务逻辑应该抽离：

例如：

```
hooks/

services/

utils/
```


---

# 10. 组件性能规范


组件设计需要考虑：


## 避免无效渲染


例如：

- 不必要响应式数据；
- 不必要状态更新。


---

## 合理使用缓存


根据框架能力使用：

- memo；
- computed；
- cache。


---

## 列表优化


大量数据展示时考虑：

- 分页；
- 虚拟列表；
- 懒加载。


---

# 11. AI Coding Agent 组件开发规则


AI 创建组件前必须分析：


```
Requirement

↓

Design

↓

Existing Components

↓

New Component
```


确认：

- 是否已有类似组件；
- 是否应该复用；
- 组件职责是否明确。


---

AI 不应该：

## 11.1 重复创建组件


已有组件满足需求时：

禁止重新实现。


---

## 11.2 创建万能组件


禁止：

```
CommonComponent

BaseComponent

UniversalComponent
```


成为大量业务入口。


---

## 11.3 随意修改公共组件


公共组件修改必须评估：

- 使用范围；
- 影响页面；
- 回归风险。


---

# 12. 组件检查清单


提交前检查：


```
[ ] 组件职责明确

[ ] Props设计合理

[ ] Events命名清晰

[ ] 无重复组件

[ ] 无过度抽象

[ ] 类型定义完整

[ ] 已验证影响范围
```


---

# 13. 总结


组件设计规范用于保证：


```
页面

+

组件

+

业务逻辑

+

AI生成代码
```


保持清晰的结构。


优秀组件应该：

- 职责明确；
- 易复用；
- 易维护；
- 易测试。
