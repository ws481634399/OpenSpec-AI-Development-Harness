# API规范

> 版本：v0.1  
> 类型：工程通用规范  
> 作用域：OpenSpec Workspace


# 1. 文档目的


本文档定义软件系统 API 设计和管理规范。


目标：

- 保证接口设计一致；
- 提升前后端协作效率；
- 降低接口维护成本；
- 使 AI Coding Agent 能够按照统一规则设计和修改接口。


---

# 2. API设计原则


## 2.1 面向资源设计


API 应优先描述业务资源，而不是操作行为。


推荐：

```
GET /orders/{id}
```


表示：

获取订单资源。


不推荐：

```
GET /getOrderById
```


---

## 2.2 接口职责明确


一个接口应该承担明确职责。


避免：

- 一个接口完成多个无关业务；
- 接口返回大量无关数据；
- 根据不同参数产生完全不同逻辑。


---

## 2.3 保持接口稳定


API 一旦发布，应保持兼容。


修改已有接口时：

优先：

- 增加字段；
- 增加新接口；
- 使用版本升级。


避免：

- 修改字段含义；
- 删除已有字段；
- 改变返回结构。


---

# 3. URL设计规范


## 3.1 使用名词表示资源


推荐：

```
/users

/orders

/products
```


避免：

```
/getUsers

/createOrder

/deleteProduct
```


---

## 3.2 使用复数形式


推荐：

```
GET /orders
GET /users
```


避免：

```
GET /order
GET /user
```


---

## 3.3 资源层级


合理表达资源关系。


例如：


获取订单下商品：


```
GET /orders/{orderId}/items
```


---

避免过深层级：


```
/users/{id}/orders/{id}/items/{id}/xxx
```


复杂关系应通过查询参数表达。


---

# 4. HTTP方法规范


## GET


用途：

查询资源。


示例：

```
GET /orders/10001
```


要求：

- 不修改数据；
- 可重复调用。


---

## POST


用途：

创建资源或执行复杂操作。


示例：

```
POST /orders
```


---

## PUT


用途：

整体更新资源。


示例：

```
PUT /orders/10001
```


---

## PATCH


用途：

部分更新资源。


示例：

```
PATCH /orders/10001
```


---

## DELETE


用途：

删除资源。


示例：

```
DELETE /orders/10001
```


---

# 5. 请求设计规范


## 5.1 参数命名


参数名称应该表达业务含义。


推荐：

```json
{
  "customerId": "10001",
  "orderStatus": "PAID"
}
```


避免：

```json
{
  "id": "10001",
  "type": "1"
}
```


---

## 5.2 分页参数


统一使用：

```
page

size
```


示例：


```
GET /orders?page=1&size=20
```


---

## 5.3 时间格式


统一使用标准时间格式。


推荐：

```
2026-08-23T10:00:00Z
```


避免：

```
20260823100000
```


---

# 6. 响应结构规范


接口返回应该保持统一结构。


推荐：


```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```


字段说明：


|字段|说明|
|-|-|
|code|业务状态码|
|message|提示信息|
|data|业务数据|


---

# 7. 分页响应规范


分页接口应该返回分页信息。


示例：


```json
{
  "code":0,
  "message":"success",
  "data":{
    "items":[],
    "page":1,
    "size":20,
    "total":100
  }
}
```


---

# 8. 错误处理规范


## 8.1 使用统一错误结构


示例：


```json
{
  "code":40001,
  "message":"订单不存在",
  "data":null
}
```


---

## 8.2 错误码规范


错误码应该具有明确含义。


例如：


```
10000

用户相关错误


20000

订单相关错误


30000

支付相关错误
```


---

# 9. API版本管理


## 9.1 重大变化需要版本升级


示例：


```
/api/v1/orders

/api/v2/orders
```


---

## 9.2 非破坏性修改


以下通常不需要升级版本：

- 增加返回字段；
- 增加新的可选参数；
- 增加新的接口。


---

# 10. 接口文档要求


每个接口应该包含：


- 接口描述；
- 请求方式；
- 请求参数；
- 响应结构；
- 错误说明；
- 示例。


---

---

# 12. API变更要求


API修改必须属于 Change。


流程：


```
Requirement

↓

Change

↓

Design

↓

API修改

↓

Test Evidence
```


---

# 13. API安全要求


接口设计需要考虑：


- 身份认证；
- 权限控制；
- 参数校验；
- 数据脱敏。


禁止：

- 返回敏感信息；
- 绕过权限检查；
- 直接暴露内部数据结构。


---
