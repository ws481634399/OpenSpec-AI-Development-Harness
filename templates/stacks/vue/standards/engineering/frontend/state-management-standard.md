# 前端状态管理规范

> 版本：v0.1  
> 类型：前端工程规范  
> 作用域：OpenSpec Workspace


# 1. 文档目的


本文档定义前端应用中状态管理的设计原则、使用规范和维护要求。


目标：

- 明确不同类型状态的管理方式；
- 降低组件之间的数据耦合；
- 保证状态流转清晰可追踪；
- 指导 AI Coding Agent 正确设计和修改前端状态。


---

# 2. 状态管理定位


状态管理用于管理前端应用运行过程中的数据状态。


状态包括：


```
用户状态

页面状态

业务状态

服务端数据状态

应用配置状态
```


状态管理的目标：

```
数据可控

+

状态流向明确

+

修改可追踪
```


---

# 3. 状态分类


前端状态应该根据生命周期和作用范围进行分类。


主要分为：


```
组件状态

页面状态

全局状态

服务端状态
```


---

# 3.1 组件状态


定义：

仅当前组件使用的状态。


例如：

- 表单输入值；
- 弹窗显示状态；
- 展开/收起状态。


管理方式：

```
组件内部状态
```


示例：

```typescript
const visible = ref(false);
```


不应该：

将所有组件状态放入全局 Store。


---

# 3.2 页面状态


定义：

当前页面范围内使用的状态。


例如：

- 页面查询条件；
- 当前页面筛选条件；
- 页面临时数据。


管理方式：

根据复杂度选择：

- 页面组件状态；
- 页面级 Hook。


---

# 3.3 全局状态


定义：

多个页面或多个业务模块共享的数据。


例如：

- 登录用户信息；
- 权限信息；
- 应用主题；
- 全局配置。


管理方式：

使用统一状态管理方案。


例如：

```
Pinia

Redux

Zustand
```


---

# 3.4 服务端状态


定义：

来自后端 API 的业务数据。


例如：

- 商品列表；
- 订单信息；
- 用户详情。


管理方式：

优先使用：

- 请求缓存；
- 数据同步工具；
- API层管理。


不要简单全部复制到全局 Store。


---

# 4. 状态选择原则


状态存放位置应该遵循：


```
使用范围越小

↓

状态位置越靠近组件


使用范围越大

↓

状态位置越靠近全局
```


---

# 5. 状态设计原则


## 5.1 单一数据来源


同一个业务状态应该只有一个真实来源。


避免：


```
Store保存一份

组件保存一份

页面保存一份
```


导致数据不一致。


---

## 5.2 状态最小化


只保存必要状态。


避免保存：

- 可以计算得到的数据；
- 重复数据；
- 临时展示数据。


例如：


不推荐：

```typescript
state = {

  firstName,

  lastName,

  fullName

}
```


推荐：

```typescript
state = {

  firstName,

  lastName

}
```


通过计算得到：

```
fullName
```


---

## 5.3 状态命名清晰


状态名称应该表达业务含义。


推荐：

```typescript
currentUser

orderList

paymentStatus
```


避免：

```typescript
data

info

value
```


---

# 6. Store设计规范


## 6.1 Store职责


Store应该负责：

- 状态保存；
- 状态修改；
- 状态相关逻辑。


不应该：

- 包含大量页面展示逻辑；
- 直接控制组件行为。


---

# 6.2 Store拆分原则


按照业务领域拆分。


推荐：

```
stores/

├── user.ts

├── order.ts

└── product.ts
```


避免：

```
appStore.ts
```


包含所有业务。


---

# 6.3 Store命名规范


推荐：


```
useUserStore

useOrderStore
```


避免：

```
store1

commonStore
```


---

# 7. 状态修改规范


## 7.1 禁止直接修改共享状态


共享状态应该通过定义的方法修改。


推荐：


```
Action

↓

Update State
```


避免：

组件直接修改 Store 内部数据。


---

## 7.2 状态变化应该可追踪


重要业务状态变化应该明确。


例如：


```
订单状态：

CREATED

↓

PAID

↓

COMPLETED
```


不要：

隐藏状态转换逻辑。


---

# 8. 异步状态管理


异步数据应该明确处理：


```
Loading

Success

Error
```


例如：


```typescript
{
 loading:false,
 data:[],
 error:null
}
```


避免：

请求状态不可感知。


---

# 9. 状态持久化规范


需要持久化的状态应该明确。


适合：

- 登录Token；
- 用户偏好；
- 系统配置。


不适合：

- 页面临时数据；
- 查询条件。


---

持久化需要考虑：

- 安全性；
- 数据有效期；
- 清理机制。


---

# 10. 状态与组件关系


推荐结构：


```
Page

 |

 |

Component

 |

 |

Store / API
```


组件不应该：

直接依赖大量全局状态。


---

# 11. AI Coding Agent 状态修改规则


AI 修改状态管理代码前必须读取：


```
delivery/

design.md

+

frontend standards

+

existing implementation
```


确认：


- 状态所属范围；
- 数据来源；
- 修改影响。


---

AI 不应该：


## 11.1 随意新增全局状态


如果组件内部可以解决：

不要创建 Store。


---

## 11.2 重复维护状态


禁止：

同一数据多个地方保存。


---

## 11.3 修改公共 Store 不评估影响


修改全局状态必须分析：

- 使用页面；
- 依赖组件；
- 回归风险。


---

# 12. 状态管理检查清单


提交前检查：


```
[ ] 状态分类正确

[ ] 数据来源唯一

[ ] Store职责明确

[ ] 无重复状态

[ ] 异步状态处理完整

[ ] 修改影响已评估

[ ] 测试已验证
```


---

# 13. 总结


状态管理规范用于保证：


```
数据

+

组件

+

业务逻辑

+

AI开发行为
```


保持一致。


合理的状态管理应该：

- 范围明确；
- 来源唯一；
- 修改可追踪；
- 易维护。
