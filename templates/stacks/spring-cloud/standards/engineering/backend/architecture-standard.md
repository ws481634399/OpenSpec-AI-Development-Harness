# 后端架构规范

> 版本：v0.1  
> 类型：后端工程规范  
> 作用域：OpenSpec Workspace


# 1. 文档目的


本文档定义后端系统架构设计规范。


目标：

- 建立清晰的系统架构边界；
- 规范服务拆分方式；
- 指导领域建模和模块设计；
- 保证系统具备可扩展性和可维护性；
- 为 AI Coding Agent 提供架构设计约束。


---

# 2. 架构设计原则


## 2.1 业务驱动设计


系统架构应该围绕业务能力设计。


架构设计应优先考虑：

```
业务边界

+

领域模型

+

系统职责
```


而不是简单按照技术模块拆分。


---

## 2.2 高内聚低耦合


模块和服务应该：

- 职责明确；
- 边界清晰；
- 减少不必要依赖。


避免：

- 跨模块直接访问内部实现；
- 公共模块承载大量业务逻辑。


---

## 2.3 演进式架构


架构应该支持业务持续变化。


设计时考虑：

- 当前需求；
- 未来扩展；
- 维护成本；
- 技术复杂度。


避免：

- 过度设计；
- 为不存在的问题引入复杂架构。


---

# 3. 分层架构规范


后端系统推荐采用分层架构。


基本结构：


```
Interface Layer

        ↓

Application Layer

        ↓

Domain Layer

        ↓

Infrastructure Layer
```


---

# 3.1 接口层（Interface Layer）


职责：

负责系统外部交互。


包含：

- Controller；
- API入口；
- 请求参数转换；
- 响应结果封装。


不负责：

- 核心业务判断；
- 数据持久化。


示例：

```
OrderController
```


职责：

```
接收请求

↓

调用应用服务

↓

返回结果
```


---

# 3.2 应用层（Application Layer）


职责：

负责业务流程编排。


包含：

- Application Service；
- Use Case；
- 事务控制。


负责：

```
多个领域能力组合
```


不负责：

- 具体业务规则实现。


---

# 3.3 领域层（Domain Layer）


职责：

承载核心业务逻辑。


包含：

- Entity；
- Value Object；
- Domain Service；
- Domain Event。


领域层应该表达：

```
业务规则

+

业务约束

+

领域行为
```


---

# 3.4 基础设施层（Infrastructure Layer）


职责：

提供技术实现。


包含：

- 数据访问；
- 外部服务调用；
- 消息中间件；
- 文件存储。


例如：

```
OrderRepositoryImpl
```


---

# 4. DDD设计规范


## 4.1 领域边界


领域模型应该围绕业务能力划分。


例如：


```
订单领域

商品领域

库存领域

支付领域
```


每个领域拥有：

- 自身模型；
- 自身规则；
- 自身职责。


---

## 4.2 实体（Entity）


实体具有：

- 唯一身份；
- 生命周期；
- 业务行为。


例如：

```
Order
```


不应该：

仅作为数据对象存在。


---

## 4.3 值对象（Value Object）


值对象描述业务概念。


特点：

- 无唯一身份；
- 通常不可变。


例如：

```
Money

Address

OrderAmount
```


---

## 4.4 领域服务（Domain Service）


当业务规则：

- 不属于单个实体；
- 涉及多个领域对象；


可以使用领域服务。


例如：

```
OrderPricingService
```


---

# 5. 微服务设计规范


## 5.1 服务边界


微服务应该按照业务能力拆分。


推荐：


```
订单服务

库存服务

支付服务

用户服务
```


---

## 5.2 服务自治


每个服务应该拥有：


- 独立业务模型；
- 独立数据管理；
- 独立演进能力。


---

## 5.3 服务间通信


服务之间应该通过明确接口通信。


例如：

- HTTP API；
- RPC；
- 消息事件。


禁止：

直接访问其他服务数据库。


---

# 6. 模块设计规范


模块应该按照职责组织。


推荐：

```
order-service

├── interface

├── application

├── domain

└── infrastructure
```


---

# 7. 数据归属规范


数据应该属于业务拥有方。


例如：

订单数据：

属于：

```
订单服务
```


其他服务：

通过接口或事件获取。


禁止：

多个服务共同维护同一业务数据。


---

# 8. 事件驱动规范


跨服务业务协作优先考虑事件。


例如：


```
订单创建

↓

OrderCreated Event

↓

库存扣减

↓

支付流程
```


事件应该包含：

- 事件名称；
- 业务数据；
- 发生时间；
- 来源。


---

# 9. AI Coding Agent 架构设计规则


AI 进行架构设计前必须读取：


```
delivery/

design.md

+

product/

+

standards/engineering/backend/

+

implementation/
```


分析：

- 当前系统结构；
- 服务边界；
- 影响范围；
- 技术约束。


---

AI 不应该：


## 9.1 随意拆分微服务


服务拆分必须有：

- 业务依据；
- 边界分析；
- 成本评估。


---

## 9.2 绕过领域模型


复杂业务不能直接：

```
Controller

↓

Database
```


---

## 9.3 引入无必要架构复杂度


例如：

没有实际需求时：

- 增加复杂中间层；
- 引入新的架构模式。


---

# 10. 架构变更管理


架构调整必须通过 Change。


流程：


```
Requirement

↓

Architecture Analysis

↓

Design

↓

Implementation

↓

Validation
```


重大架构决策应该记录：


```
delivery/

changes/

ADR/
```


---

# 11. 架构检查清单


设计评审时检查：


```
[ ] 服务边界明确

[ ] 分层职责清晰

[ ] 领域模型合理

[ ] 数据归属明确

[ ] 服务通信方式明确

[ ] 架构复杂度合理

[ ] 风险已评估
```


---

# 12. 总结


后端架构规范用于保证：


```
业务领域

+

系统架构

+

技术实现

+

AI开发过程
```


保持一致。


良好的后端架构应该：

- 面向业务；
- 边界清晰；
- 易演进；
- 可维护。
