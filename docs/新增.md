# 一、总体架构目标

最终 OpenSpec 应形成两级 Delivery：

​```text
Workspace Delivery
        +
Repository Delivery
```

Workspace 负责：

```
Requirement
Explore
PRD
System Design
Task Decomposition
Cross-Repository Coordination
Evidence Aggregate
Review
Converge
Archive
```

Repository 负责：

```
Repository-specific Delivery Unit
Dev
Test
Implementation Evidence
```

核心边界：

> Task 阶段是 Workspace Change 向 Repository Delivery 分解的边界。

------

# 二、Git 模型：Workspace + Git Submodule

正式采用：

```
Workspace Git Repository
        +
implementation/* Git Submodules
```

目标结构：

```
workspace/
├── .git/
├── .gitmodules
│
├── .sdd/
├── standards/
├── product/
├── delivery/
│
└── implementation/
    ├── backend/       Git Submodule
    ├── frontend/      Git Submodule
    └── ai/            Git Submodule
```

Workspace Git：

- 管理 Workspace 知识
- 管理 Delivery
- 管理 `.gitmodules`
- 管理每个 Submodule 的 Commit Pointer

Workspace Git 不直接管理：

- backend 内部 Git 历史
- frontend 内部 Git 历史
- ai 内部 Git 历史

每个 Submodule：

- 独立 Git Repository
- 独立 Branch
- 独立 Commit
- 独立 PR
- 独立 Repository Delivery

注意：

Git Submodule 工作树中的 `.git` 通常是指向父仓 `.git/modules/...` 的文件，而不是普通 `.git/` 目录。

设计文档表达领域关系即可，不要错误假设物理 `.git` 一定是目录。

------

# 三、`.gitmodules` 与 `.sdd/repositories.yaml` 职责必须分离

不要让 Git Submodule 替代 OpenSpec Repository Registry。

定义：

```
.gitmodules
= Git Repository Mapping

.sdd/repositories.yaml
= OpenSpec Repository Registry
```

例如：

```
mode: multi

repositories:
  - id: backend
    path: implementation/backend

  - id: frontend
    path: implementation/frontend

  - id: ai
    path: implementation/ai
```

OpenSpec 使用 `repositories.yaml` 做：

- Repository ID 解析
- Context Loading
- Repository Impact
- Delivery Unit Ownership
- Evidence Attribution
- Review Aggregation
- Workflow Routing

Git 使用 `.gitmodules` 做：

- remote URL
- local path
- Submodule Commit Pointer

后续 Validation / Doctor 应能够校验：

```
repositories.yaml
        ↕
.gitmodules
```

路径是否一致。

└── changes/

`CHG-0001` 是一次完整需求变更的第一追踪 ID。

Change 内部再组织 Feature Tree Path。

# 六、Feature Tree 固定四级结构

当前设计正式采用四级 Feature Tree：

```
Level 1
  ↓
Level 2
  ↓
Level 3
  ↓
Story
```

例如：

```

  ↓
FEAT-001-02
  ↓
FEAT-001-02-03
  ↓
STORY-001-02-03-01
```

其中：

> Story 是 Feature Tree 最小产品能力节点。

不要把 Repository-specific Delivery Unit 叫 Story。

# 七、Change 内必须保存完整 Feature Tree Path

目标目录：

```
delivery/
└── changes/
    └── CHG-0001/
        ├── metadata.yaml
        ├── requirement.md
        ├── exploration.md
        ├── prd.md
        ├── design.md

            └── FEAT-001-02/

不要使用：

```

用户认证/
用户注册/
```

名称允许变化，ID 必须稳定。

# 八、Change Metadata 保存完整 Feature Path

不要只保存：

```

```

调整为完整路径：

    name: 账户能力

Change Feature 归属必须同时通过：

```
Directory Path
+

```

表达。

`product/feature-tree.yaml` 仍然是 Feature Tree 唯一权威来源。

Delivery 不维护第二套 Feature Tree。

# 九、sdd-explore 负责 Requirement → Story Mapping

    ↓

# 十、Design 阶段不创建 Delivery Unit

这是本次设计必须明确的硬约束。

Design 阶段负责：

```
System Technical Design
+
Repository Impact
+
Cross-Repository Contract
```

Design 必须记录：

- 涉及哪些 Repository
- 每个 Repository 的技术职责
- API Contract
- Event Contract
- Data Contract
- Repository Dependencies
- Integration Boundary
- Migration Impact
- Cross-Repository Sequence / Dependency

例如：

```
## Repository Impact

### backend

- 新增注册 API
- 实现 User Domain Logic
- 增加数据库 Migration


### frontend

- 新增注册页面
- 接入注册 API


### ai

- 接入注册风险检测


## Cross-Repository Dependencies

frontend
    ↓ HTTP API
backend
    ↓ risk-check
ai
```

但是 Design 阶段不得产生：

```
DU-BE-001
DU-FE-001
DU-AI-001
```

原因：

> Design 回答“系统如何实现以及哪些仓受到影响”。

> Task 才回答“如何将 Design 拆成正式可交付单元”。

# 十二、正式引入 Delivery Unit Domain Model

新增领域对象：

```
Delivery Unit
```

定义：

> Delivery Unit 是一个 Workspace Change 在一个具体 Repository 中的实现交付单元。

关系：

```
Requirement
    ↓
Change
    ↓
Feature Path
    ↓
Story
    ↓
1 : N
    ↓
Delivery Unit
    ↓
1 : 1
    ↓
Repository
```

例如：

```
CHG-0001

STORY-001-02-03-01

├── DU-BE-001 → backend
├── DU-FE-001 → frontend
└── DU-AI-001 → ai
```

硬约束：

> 一个 Delivery Unit 在 v0.5 中必须只属于一个 Repository。

如果一个交付单元跨 Repository：

必须拆成多个 DU。

# 四十一、硬约束

最终设计必须明确以下硬约束：

1. Workspace 是独立 Git Repository。
2. implementation 多仓采用 Git Submodule。
3. `.gitmodules` 管 Git 引用。
4. `.sdd/repositories.yaml` 管 OpenSpec Repository Registry。
5. CHG 是最外层 Delivery 容器。
6. Change 根目录保存 requirement / explore / prd / design。
7. Change 内按 L1 → L2 → L3 → Story 保存完整 Feature Path。
8. Story 是 Feature Tree 最小产品能力节点。
9. Design 只定义 Repository Impact / Contract，不创建 DU。
10. Task 阶段正式创建 Delivery Unit。
11. Change 1:N Delivery Unit。
12. Delivery Unit 1:1 Repository。
13. Workspace Story 下保存全部 DU 的协调视图。
14. Repository 只 materialize 属于自己的 DU。
15. Repository Delivery 使用 CHG → L1 → L2 → L3 → Story → DU 完整路径。
16. Repository 不复制 Workspace PRD / Design。
17. Dev/Test 必须绑定具体 Delivery Unit。
18. Repository Evidence 属于 Repository Delivery。
19. Workspace 只聚合 Evidence Reference / Summary。
20. Review 在 Workspace 做跨仓检查。
21. Converge 只在 Workspace 做长期知识沉淀。
22. Workspace 最终 Git Commit 锁定所有 Submodule Commit Pointer。
23. Transition Service 仍然是 Workspace Lifecycle 唯一状态推进入口。
24. Machine Gate 仍然只做确定性验证。
25. 不引入 Agent Runtime。
26. 不让 Repository Delivery 再复制一套完整 SDD 生命周期。
