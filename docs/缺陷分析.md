# CHG-0003 工程缺陷清单

## 缺陷 1：OpenSpec CLI v0.x 自身代码缺陷

### 1.1 workflow 引擎 `join is not defined`

- **现象**：`openspec workflow run default --change CHG-0003` 报内部错误 `join is not defined`
- **缺陷本质**：工作流引擎源码引用了未定义的 `join` 函数，导致整个生命周期状态推进（dev→test→review→converge）全部失败
- **影响**：4 次阶段推进均需复刻核心逻辑的临时脚本绕过，CLI 自动化能力完全丧失

### 1.2 参数解析吞空值

- **现象**：`openspec du create --dependencies "" --acceptance ...` 导致 `dependencies` 字段错位，`--acceptance` 的值被误识别为依赖
- **缺陷本质**：CLI 参数解析器未正确处理空字符串参数，把空值"吞掉"后位移后续参数
- **影响**：DU 注册失败 1 轮，需省略空依赖参数重新注册

### 1.3 archive 命令缺跳过确认选项

- **现象**：`openspec change archive CHG-0003` 触发交互式 `[No]` 确认，沙箱自动取消
- **缺陷本质**：命令缺少 `--yes/-f/--no-confirm` 选项，无法在 CI/沙箱等非交互环境执行
- **影响**：归档必须复刻 archiveChange 核心逻辑（Move-Item + Edit）

### 1.4 gate approve 不支持 `--reviewer`

- **现象**：`openspec gate approve --reviewer user` 报 `unknown option '--reviewer'`
- **缺陷本质**：人工审批接口未暴露 reviewer 字段，审批信息无法通过 CLI 完整写入
- **影响**：每个阶段人工门禁都得绕过 CLI 直接调 writeHumanGate 函数

### 1.5 CLI 命令参数语义不一致

- **现象**：`openspec status --change CHG-0003` 报 `unknown option '--change'`；`openspec workflow run --stage dev` 报 `unknown option '--stage'`
- **缺陷本质**：不同子命令的参数命名不统一（`status` 不接受 `--change`，但 `workflow run` 接受），用户体验割裂
- **影响**：需多次试错才能确定正确参数组合

## 缺陷 2：metadata.yaml machine gate 写入依赖人工触发

- **现象**：converge 阶段 convergence.md 已产出、human gate 已写，但 status 仍停留在 `testing`，machine gate 节点缺失
- **缺陷本质**：状态机设计上 machine gate 应是 stage 推进的前置条件（自动调用 validator），但实现上 CLI 未在 stage 推进时自动写入 machine gate，变成人工补写
- **影响**：converge 收尾需手动计算 artifact-hash + 手填 machine gate 节点，破坏自动化；review-report 阶段同样存在此问题

## 缺陷 3：沙箱与全局工具链路径冲突

- **现象**：沙箱禁止访问 `C:\Users\2025\AppData\Roaming\npm\node_modules` 和 `D:\maven-repository`
- **缺陷本质**：沙箱设计假设所有工具链在工作区内，但实际 npm 全局包和 Maven 本地仓库都在用户目录下
- **副作用**：
  - 无法直接读取 archiveChange 源码做精准复刻，只能凭经验黑盒模拟核心逻辑
  - Maven 必须改用工程内临时仓库 `.m2-sandbox/`（通过 `-Dmaven.repo.local` 指定），污染工作区，且需在 .gitignore 排除
  - npm 命令日志写入失败，虽能拿到 stdout 但调试链路不完整

## 缺陷 4：design.md 模板与机检器契约不一致

- **现象**：模板 `## 1. 当前状态` 下直接接 `### 1.1 子标题` 被机检报 `section 内容为空`
- **缺陷本质**：模板未在每个 section 下预留引行占位（如 `> 本节说明 ...`），但机检器又强制要求 section 必须有正文，两者契约不一致
- **影响**：design 阶段机检回退 2 轮，需手动补引行才能通过

---

## 缺陷 5：模板占位符未在创建时强制替换

- **现象**：design.md 中遗留 `{{proposal-summary}}` `{{interface-contract}}` 占位符，直到 `gate verify` 才被发现
- **缺陷本质**：机检器应在 `create` 阶段（sdd-design 创建文档时）就强制替换占位符，而不是等到 `gate verify` 阶段才报错
- **影响**：缺陷发现时机滞后，导致已写完的文档返工

## 缺陷 6：archive 路径变更的 git rename 行为未文档化

- **现象**：`openspec change archive` 内部通过 Move-Item 移动目录后，git 识别为 17 个 100% rename
- **缺陷本质**：archive 命令未在文档中明确说明"目录移动会触发 git rename 而非 delete + add"，团队可能误以为归档会丢失 history
- **正面意义**：rename 保留 history 是好设计，但缺文档化导致信任成本高
- **影响**：归档操作前需额外验证 history 保留

---

## 缺陷 7：DU metadata 状态同步滞后

- **现象**：DU 物化后 workspace 与 repo 两边的 DU metadata 状态不一致，需用 `openspec du sync-status` 手动刷新
- **缺陷本质**：DU 完成事件未自动触发两边状态同步，sync-status 应是事件驱动而非手动命令
- **影响**：converge 阶段 submodule-pointer-aligned 机检因 DU metadata 状态滞后而失败 1 轮

---

## 缺陷 8：metadata YAML 模板尾部结构易损坏

- **现象**：metadata.yaml 在多次编辑后出现尾部 YAML 结构损坏（8 节点结构错乱）
- **缺陷本质**：YAML 文件用流式风格（`{ ... }` 嵌套）而非块式风格（缩进），人工编辑极易破坏缩进/逗号/括号匹配
- **影响**：需手动修复 8 节点结构才能让 CLI 重新识别；建议模板改为块式 YAML 风格

---

## 缺陷 9：harness v0.2.0 bind traversal bug

- **现象**：harness 在生成 feature-tree 时把"story 直接挂在 L2 下"的分支错误嵌套进 L3 循环，导致 v1 feature 树失败
- **缺陷本质**：bind 遍历算法未区分"story 直接挂 L2"和"story 挂 L3"两种结构
- **影响**：v1 Changes 必须迁移到 v2 四级 schema 才能通过机检；memory 中已记录此缺陷

## 缺陷 10：Change 级全局验收标准在多 Story 模式下无专门检查点

- **发现**：Phase 4.2 交接链审计（2026-09-04，全链 10 衔接点完整性/冗余复查）
- **现象**：三级规格分层后，review 检查点下沉到 Story 级（story-review 仅对照 story-spec.md §5 的 Story 验收标准）；change-prd.md §5 全局验收标准（跨 Story 端到端验收点）没有任何阶段的 Gate 检查点做逐条对照
- **缺陷本质**：Story 分层验收的并集 ≠ 全局验收——各 Story AC 全部通过只能证明局部正确，跨 Story 集成场景（如端到端流程、跨仓契约联动）的全局验收点存在归属空白。设计上默认由 converge Human Gate 兜底，但 converge 机检（all-predecessors-accepted 等）不含 AC 对照，人审也无结构化对照表支撑
- **影响**：全局验收遗漏风险被静默传递到交付后；Story 拆分越细，跨 Story 缝隙越容易漏验
- **候选方案**（2026-09-04 决策：选 A，已实施）：
  - A. converge 收口补强：sdd-converge 模板加「全局验收标准对照表」节（change-prd §5 逐条 → 证据引用），gate.yaml 声明 human-check（推荐，改动小且符合 converge 收口定位）✅ 已实施
  - B. 新增 Change 级 review 检查点（重，破坏 4.1 轻量化分级，不推荐）
  - C. 接受人审兜底现状，仅在文档声明该边界（最轻，风险留存）
